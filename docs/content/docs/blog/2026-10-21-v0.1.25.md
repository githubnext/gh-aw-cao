CAO [v0.1.25](https://github.com/githubnext/gh-cao/releases/tag/v0.1.25) is a stable release, not a pre-release. The comparison from v0.1.24 lists six commits. This post covers the one behavior change I could confirm in the repository files at the release tag, plus the documentation updates that go with it. It leaves out a debug-logging commit and a compliance-ledger refresh that do not change how you operate CAO.

## `gh cao setup` prepares the runtime for you

Before this release, setup assumed you had already prepared the runtime and policy. Now `gh cao setup` is the single guided entry point ([#19372](https://github.com/githubnext/gh-cao/pull/19372)). The [CAO Commands reference](https://github.com/githubnext/gh-cao/blob/v0.1.25/docs/cao-cli.md) says that, run from the root of an existing GitHub checkout, it:

- adds missing monitoring runtime files and a missing baseline policy;
- configures exact repository scope, authentication, and Actions-backed Pages;
- stages the runtime package with `gh-aw` in an isolated checkout, then verifies the selected stable release's provenance and file checksums before adding files.

Setup fails closed. Existing policy is read rather than replaced, and invalid policy or conflicting runtime files stop the run. A complete runtime install is reused, so use `gh cao update --campaign root` to upgrade. A missing `gh-aw` is installed at the catalog's minimum version, but setup does not silently upgrade an older or broken one.

Setup does not create repositories, enroll campaigns, or dispatch workflows. Create or clone the control repository yourself first. `gh cao init` remains available as an optional, policy-only command for scripting.

The documentation also notes that this change is in source at v0.1.25. Merging source does not update an installed binary, and v0.1.24 still requires prior runtime and policy preparation.

## Review before you publish

After configuration, interactive setup offers a separate "Commit and push these CAO monitoring changes? [y/N]" prompt ([#19372](https://github.com/githubnext/gh-cao/pull/19372)). The default is No. It shows a file summary and policy diff, and only the exact runtime and package files that setup prepared are eligible.

Publication has strict preconditions: an empty real index, a single matching `origin` push destination, and a default-branch checkout exactly synchronized with the remote. The push is normal, with no force, extra tags, or protection bypasses. If any precondition fails, publish manually. Unattended or CI setup never commits or pushes.

On success, setup reports Actions and dashboard links as "deployment pending" and returns without dispatching or waiting. With `--json`, the output includes `publication.status`.

## Quickstart and guide updates

The quickstart now installs the CAO extension directly ([#19360](https://github.com/githubnext/gh-cao/pull/19360)). The control-repository guidance clarifies checkout and ownership next to the setup commands ([#19356](https://github.com/githubnext/gh-cao/pull/19356)). The App and personal access token guides were refreshed for extension installation and optional reviewed publication ([#19372](https://github.com/githubnext/gh-cao/pull/19372)).

## What to do next

If you operate a control plane, read the [release page](https://github.com/githubnext/gh-cao/releases/tag/v0.1.25) and upgrade your installed `gh cao` extension; source changes alone do not change your binary. For a new control repository, clone it, run `gh cao setup` from its root, and review the policy diff before accepting the optional commit. For an existing install, keep using `gh cao update --campaign root`. I could not verify any other behavior changes in this release.
