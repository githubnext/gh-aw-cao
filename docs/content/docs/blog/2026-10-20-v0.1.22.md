CAO [v0.1.22](https://github.com/githubnext/gh-cao/releases/tag/v0.1.22) is a pre-release, not a stable release. The comparison from v0.1.21 lists 76 commits. This post covers the changes whose behavior I could confirm in the repository files at the release tag. It leaves out routine debug-logging, test-fixture, and documentation-styling commits, and anything I could not verify.

## Operator commands now run natively in `gh cao`

The Go extension now carries the operator-facing command surface. A rewrite replaces the Node runtime bridge with native onboarding, management, evidence queries, computations, and a read-only MCP server ([#18745](https://github.com/githubnext/gh-cao/pull/18745)). A follow-up moves operator commands to `gh cao` and makes the installer verify published release binaries before installing them ([#18767](https://github.com/githubnext/gh-cao/pull/18767)).

In the [CAO Commands reference](https://github.com/githubnext/gh-cao/blob/v0.1.22/docs/cao-cli.md), the read-only analysis commands run as native Go with pure-Go SQLite access. Node.js 24 or later is still required to install the pipeline runtime, but not to run the Go operator commands afterward. Two administration tasks, `doctor` and `setup-auth hosted-cli`, remain Node-only and have no Go equivalent.

The installer fails closed. A download is rejected unless the asset's exact checksum and embedded version match, and verification finishes before an existing binary is replaced.

## Governance reaches standalone workflows

Until now, admission and rollout policy applied to campaigns. This release extends the same gates to standalone agentic workflows, with bounded multi-repository execution, target-specific modes, and fail-closed identity and scope checks ([#18995](https://github.com/githubnext/gh-cao/pull/18995)).

A workflow declares one of three roles: `orchestrator`, `worker`, or `standalone`. A standalone workflow must be declared under `control-plane.workflows`, and its identity must match its compiled workflow reference. As with campaigns, a manual dispatch can narrow a run but cannot promote its mode, add scope, or enable a workflow. See [Admission](https://github.com/githubnext/gh-cao/blob/v0.1.22/docs/admission.md) and [standalone workflow configuration](https://github.com/githubnext/gh-cao/blob/v0.1.22/docs/configuration.md#standalone-agentic-workflows).

The dashboard's **Maintenance → Governance** page is now visible only in local server `--admin` mode or to an authorized hosted administrator with a current, assured session. It stays hidden in published dashboards, ordinary local previews, and Copilot canvas mode, including through direct links ([#18998](https://github.com/githubnext/gh-cao/pull/18998)).

## Dashboard serving

The Go dashboard server can now serve a local SQLite snapshot through an explicit, read-only, loopback-only adapter ([#18860](https://github.com/githubnext/gh-cao/pull/18860)).

For hosted deployments, the Go server now refuses to start unless the site directory contains a readable, non-empty built `index.html` ([#19016](https://github.com/githubnext/gh-cao/pull/19016)). The [deployment guide](https://github.com/githubnext/gh-cao/blob/v0.1.22/docs/deployment.md) states that hosted mode serves the dashboard, sign-in, query API, and revision events from one origin, and that a hosted failure does not fall back to browser storage or a Pages deployment.

The Coolify deployment profile and its related checks were removed; generic container hosting and GitHub Pages remain ([#18902](https://github.com/githubnext/gh-cao/pull/18902)).

## Security hardening

- **Go toolchain.** Modules, CI, and the server image now require Go 1.27.3, to distrust compromised eMudhra intermediate keys ([#19130](https://github.com/githubnext/gh-cao/pull/19130)).
- **PostgreSQL TLS.** Non-loopback connections must use verified TLS (`sslmode=verify-full`). The `require` and `verify-ca` modes are rejected; use `sslrootcert` for a private CA ([#19130](https://github.com/githubnext/gh-cao/pull/19130)).
- **Snapshot downloads.** The native CLI will not follow a redirect that downgrades HTTPS to HTTP. You can pass `--manifest-sha256` for independent integrity checking, because a checksum fetched alongside a snapshot detects corruption but not a compromised publisher ([#19130](https://github.com/githubnext/gh-cao/pull/19130)).
- **Release promotion.** Promotion jobs are limited to GitHub.com read-only cache tokens, and documentation dependencies are rebuilt from the lockfile on every run ([#19001](https://github.com/githubnext/gh-cao/pull/19001)).

## What to do next

If you operate a control plane:

1. Install or refresh the extension with the installer, then run `gh cao --version` to confirm the version.
2. If you connect to a remote PostgreSQL server, confirm the connection uses `sslmode=verify-full`, since weaker modes are now rejected.
3. If you deploy a hosted dashboard, confirm the server's site directory holds the built dashboard.
4. If you used the Coolify profile, plan a different hosting path.
5. If you run standalone workflows, review the role and identity requirements before enabling them.

This is a pre-release. The evidence here comes from the repository files at the tag, and I did not run the release binaries. Read the full [release page](https://github.com/githubnext/gh-cao/releases/tag/v0.1.22) for the complete change list.
