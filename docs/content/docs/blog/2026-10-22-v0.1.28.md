CAO [v0.1.28](https://github.com/githubnext/gh-cao/releases/tag/v0.1.28) is a stable release, not a pre-release. The comparison from v0.1.27 contains one commit, [d29ce7b](https://github.com/githubnext/gh-cao/commit/d29ce7ba7a628e24988f8fbbe108396b9d037705), from pull request [#19464](https://github.com/githubnext/gh-cao/pull/19464). This post covers the behavior I could confirm in the repository files at the release tag.

## Install a standalone workflow in one command

You can now run `gh cao add repo-status` from a control repository checkout. Before this release, the quickstart had you run `gh aw add` with a full URL and then edit `.github/workflows/cao.json` by hand ([#19464](https://github.com/githubnext/gh-cao/pull/19464)).

The [CAO Commands reference](https://github.com/githubnext/gh-cao/blob/v0.1.28/docs/cao-cli.md) describes the accepted sources:

- a catalog name such as `repo-status`, optionally pinned with `repo-status@FULL_COMMIT_SHA`;
- an explicit `.md` source, including a GitHub URL or a local file;
- `--force` to overwrite installed files, and `--engine` to override the gh-aw AI engine.

Catalog names resolve to CAO's `.github/workflows/` directory rather than gh-aw's `workflows/` directory. The workflow is `repo-status`, not `daily-repo-status`. gh-aw still performs the installation and compilation. `gh cao add` does not accept custom install directories or renames, and campaign packages still use `gh cao campaigns add`.

## Registration is automatic and review-only

After gh-aw succeeds, CAO verifies the installed import and compiled lock, then registers the workflow under `control-plane.workflows`. A new entry sets `mode: review`, `max-mode: review`, and `max-repositories: 1`. Existing entries, including disables and live settings, are preserved, and repeating the command with `--force` does not reset policy. A failed install does not change policy, although files from a partial install may remain for you to inspect. The quickstart no longer asks you to register the workflow manually ([#19464](https://github.com/githubnext/gh-cao/pull/19464)).

Missing policy gets the same exact-current-repository baseline as `gh cao init`. Prepare the shared runtime separately with `gh cao setup`.

## Publication and first run need separate approvals

In an interactive session, `gh cao add` can offer to commit and push only the installation changes, using the same safeguards as setup. Pre-existing edits to an installation file, a staged index, a non-default branch, or an unsynchronized remote block automated publication. Unrelated work is never staged.

After a successful publication, a second prompt can request a first review run through `gh aw run`. The documentation says both prompts default to No. CI and non-interactive use, and unchanged repeated additions, never publish or run. CAO checks that the branch still points at the published commit before dispatch, then checks the returned run's workflow and commit. If the identity cannot be verified, it reports the outcome for manual inspection instead of retrying. Run verification needs GitHub CLI 2.87 or later. A first run can spend AI credits and create outputs, and CAO admission still applies.

## What I left out

The same commit also touches Go dependency files and unit tests. I did not describe those because they do not change how you operate CAO. I could not verify any other behavior changes in this release.

## What to do next

If you operate a control plane, read the [release page](https://github.com/githubnext/gh-cao/releases/tag/v0.1.28) and upgrade your installed extension with `gh extension upgrade gh-cao`; the documentation states that merging source does not update an installed binary. Then try `gh cao add repo-status` in a control repository and review the source, lock, and policy changes together before you publish them.
