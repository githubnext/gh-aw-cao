# Central Agentic Ops Data Acquisition Audit History

This ledger records material refreshes for [Central Agentic Ops Data Acquisition Audit](./data-acquisition-audit.md). It is intentionally compact so the audit document can focus on current acquisition paths, duplicate work, bottlenecks, and recommendations.

| Date | Refresh | Material acquisition delta | Non-material changes noted |
| --- | --- | --- | --- |
| 2026-09-25 | Budgeted GraphQL issue-status enrichment; legacy AI-credit and curator graders removed | `#13795` added `activity/collect-logs.sh` → `cao issue-status`, a new budgeted GraphQL batch lookup of non-pull-request Issue state (25-point cost budget, 500-point remaining floor, staleness-prioritized, per-repository batches) that enriches already-ingested safe-output records after each activity run; this is the repository's first production GraphQL acquisition path. Separately, `#13929` deleted all legacy per-workflow operational-value graders that lived under the shared `.github/workflows/graders/` path (including both AI-credit-auditor/optimizer graders and the `optimization-agents-md-curator` grader), and the `optimization-ai-credit-auditor.md`/`optimization-ai-credit-optimizer.md`/`optimization-agents-md-curator.md`/`optimization-skills-curator.md` producer workflows themselves no longer exist anywhere (confirmed removed by `#13654`/`#f4fa1ad0`); surviving graders now live under `<campaign>/.github/graders/*-operational-value.sh` and are invoked through a new `cao operational-value` collector (`activity/operational-value.mjs`) added by `#13746`. This removes the two-day/seven-day AI-credit `gh aw logs` overlap this audit previously recorded and closes the corresponding grader/producer rows in §2, §3.3, §5, and the API relationship diagram. | `activity/operational-value.mjs`'s per-campaign module discovery and `optimization/operational-value/optimization-token-optimizer.mjs`'s deployed-dashboard-download fallback are local processing of the already-ingested or already-deployed snapshot, not new discovery scans. |
| 2026-09-24 | Agentic workflow compaction filter | Activity compaction now retains only runs whose workflow path ends in `.lock.yml`, filters workflow-run listings to those run IDs, and retains associated safe-output and token-efficiency records only for those runs. Non-agentic Actions workflows are removed before ingestion without additional GitHub API traffic. | none |
| 2026-09-17 | Repository-bound shard consolidation | `#12556` added a `cao compact-jsonl --input-dir <shard_directory> --group <repo>=<shard_prefix>` step to `activity/collect-logs.sh`, run once per activity collection after a successful `gh aw logs` fetch for each repository. It merges each repository's accumulated wildcard shard files into a single consolidated shard before the shard directory is persisted in the `cao-activity-v3` cache, reducing per-run shard/file-count bloat. This is a local, post-collection consolidation step with no new `gh`/GitHub API traffic; the `gh aw logs --cached-logs` acquisition call, window, run-count ceiling, and paired `--runs-dir`/`--events-dir` ingestion shape recorded in the prior refresh row are unchanged. | none |
| 2026-09-17 | Token-efficiency artifact collection removed | `#12550` removed the `optimization/collect-token-efficiency.sh` invocation (and its file-existence probe) from `.github/workflows/cao-activity.yml`, superseding the acquisition path recorded in the prior refresh row below. Scheduled activity collection no longer lists `token-efficiency-observation`/`token-efficiency-lifecycle-claim` Actions artifacts or issues per-artifact `GET /actions/runs/{id}` and archive-download calls; that P1 bottleneck is now closed. The script remains at `optimization/collect-token-efficiency.sh` (still installed to `optimization/collect-token-efficiency.sh` by the Optimization campaign manifest) and is still exercised directly by unit tests, but no production workflow currently calls it. `#12524` had separately relocated the script out of `activity/collect-logs.sh` into its own file one commit earlier, and `#614bbc4c` dropped an unrelated empty-shard-set integrity check from the same workflow; neither changes the audited request shape. | `#12487` (workflow registry enrichment, already reflected in the prior refresh) is unchanged. |
| 2026-09-17 | Token-efficiency artifact collection and run-limit reversal | `activity/collect-logs.sh` (via `cao-activity.yml`) now also invokes `optimization/collect-token-efficiency.sh` once per activity run: it lists `token-efficiency-observation` and `token-efficiency-lifecycle-claim` Actions artifacts (one listing call each, the lifecycle listing paginated at 100/page), then for every matching artifact issues a `GET /actions/runs/{id}` call plus a raw archive download and unzip — new, uncached `gh api` traffic with only a client-side 30-day `jq` filter and no content-hash dedup against the shared shard cache. Separately, `cao-activity.yml`'s `REPORT_RUN_LIMIT` and `activity/logs.mjs`'s validated ceiling were raised from a 200-run maximum back up to 10,000 (default stays 10), reversing the prior lowered figure this audit had recorded. `activity/cao.mjs` ingestion was also restructured from a single `--input-dir` shard directory into paired `--runs-dir`/`--events-dir` phased shard directories so compact run properties commit before detailed events; the content-hash skip behavior is unchanged. | `activity/inventory-sources.mjs`'s paginated Actions workflow registry read (documented in the prior refresh) is unchanged. |
| 2026-09-14 | Incremental shard-based activity cache | Activity's `gh aw logs` invocation now uses `--cached-logs "<prefix>*"` instead of `--cached-jsonl`, carrying forward per-run wildcard shard files in the shared `cao-activity-v3` cache instead of one growing file; new data is written to a freshly named shard rather than rescanning the carried-forward set. `cao ingest-jsonl --input-dir` ingests the shard directory one file at a time, skipping any shard whose content hash already matches its transactions-table record, so re-runs against unchanged shards perform no re-parsing. | `cao-dashboard.yml` and other consumers use the retained shards directly. `payload-hashes.json` contains one SHA-256 entry per retained shard. |
